# Jame-ul-Uloom Website

A static website: ordinary HTML pages, plain CSS and JavaScript, as the original site was. **`public/` is the whole site; publish it as the site root.** There is nothing to build or install for publishing, no database and no login, and nothing runs on the website's own server. The site is published on GitHub Pages by `.github/workflows/deploy-pages.yml` (that workflow belongs to the repository; this package does not contain or change it).

Two jobs happen elsewhere, each in one place:
- the **weekly Bayanath video update**: a GitHub Actions workflow (`.github/workflows/update-bayanath.yml`) that runs two small Python scripts in `tools/`; it is not part of publishing the site;
- the **forms** (Feedback, Admissions enquiry, Careers): sent to a small Cloudflare Worker (`serverless/forms-worker/`) that emails the office. It has to be set up once (see "Setting up the form service"). Until then no setup message is shown on the pages: a visitor who presses Send gets their own email program opened with the message ready, and the page says only that. A form never reports a message as sent unless the service confirms it.

## Layout of the project
```
public/                    the website (publish this folder)
  index.html               the only homepage
  *.html                   main pages (About Us, Institutions, Bayanath, Contact, Support Us ...)
  <Institution>/*.html     one folder per institution (ITI, PUGirlsCollege, DegreeGirlsCollege, BCA, NCPUL,
                           EngNurSchoolDEL, EngPrimarySchoolDEL, EngGirlsHighSchool, EngBoysHighSchool,
                           ShobaehifzDel, ShobaeAlimiyathDel)
  ResidentialSchoolBanikuppa/   the Residential School site (25 pages, its own images and styles)
  portal-assets/           shared CSS and JavaScript, images, documents, videos
  data/                    bayanath-videos.json (the video list), bayanath-speakers.json (speaker exceptions)
  robots.txt, sitemap.xml  for search engines
  _headers, _redirects, .htaccess   security headers and old-address redirects (see below)
docs/                      photograph and media maps, provenance records
serverless/forms-worker/   the form service (Cloudflare Worker, plain JavaScript, no dependencies)
tools/                     the Bayanath updater, the page refresher, the optional host upload, the link checker and the tests
.github/workflows/         the weekly Bayanath update
```
115 HTML pages in total. The pages share one pattern: a header with the menu (and a drawer for phones), the page content, a footer. Each page holds its own copy, as in the original site.

## Editing the site
- **Text, pictures and links** are edited directly in the page's HTML. Pictures go in `public/portal-assets/images/` (lowercase file names); show photographs whole, never cropped (`object-fit: cover` only on decorative blurred backdrops). No MP3 audio.
- **A menu entry** has to be added to every page that has the site header (the same line appears in the desktop menu, the phone drawer and, usually, the footer). Search for an existing entry, for example `SupportUs.html`, to find each place. The Residential School pages have their own header.
- **A new page:** copy a similar page, change the `<title>`, description, canonical and `og:url`, the heading and content, then add it to `public/sitemap.xml`.
- **Search metadata** (canonical, robots, Open Graph, JSON-LD) is in each page's `<head>`. The origin is `https://jameululoom.org`. The 404 page is the only `noindex` page. JSON-LD is a `<script type="application/ld+json">` data block, which the security policy does not block. Search engines decide for themselves what to index, show or cite; nothing here guarantees a result.
- **Sitemap, robots and redirects** are maintained by hand: `public/sitemap.xml` lists exactly the indexable pages; `_redirects` and `.htaccess` carry the same legacy-address redirects (and the `/home` rule). When a page moves, add a redirect to both and check that the target exists.
- **Stylesheets:** `portal-assets/portal.css` (shared design, including the motion rules); `ResidentialSchoolBanikuppa/assets/css/` (`styles.css`, `motion.css`) for the Residential School; page-group styles in `bayanath.css`, `scholar.css`, `slideshow.css`, `connect.css`, `support.css`, `masjid.css`, `theme-light.css`. **Scripts:** `app.js` (menu, drawer, reveals, theme toggle), `theme-init.js` (sets the theme before first paint), `motion.js`, `slideshow.js`, `bayanath.js`, `forms.js`, `support.js`, `masjid.js`, `aurora.js`. The Residential School pages use the same `app.js`, `theme-init.js` and `motion.js` from `portal-assets/`.
- **Themes:** `data-theme="light|dark"` on `<html>`, saved in `localStorage` under `jame-theme`. Light is the default for a first-time visitor; a saved choice always wins. The navy pages are written with dark tokens and `theme-light.css` re-maps them for light mode, so change colours there rather than hard-coding a dark background in a page stylesheet.
- **Code style:** 4 spaces, `selector{` with the brace attached, `function(){`, single quotes, semicolons, ES5 in the scripts that run on every page.
- **Public wording:** do not publish internal notes about where content came from, scanned-document disclaimers or audit notices. Keep dated caveats that help a reader. Never merge conflicting historical dates or figures silently; label dated fees, strengths and results with the date the source gives. Do not describe an institution from text that belongs to another.

## Check before publishing
```bash
python3 tools/check_site.py                       # links, images, scripts, #ids, redirects, forbidden files, inline code
python3 -I -m unittest discover -s tools/tests -v # page, search-metadata, security-header, updater and form tests
```
Python 3.10 or newer is enough (3.12 is what the workflow uses). The form service's own tests need Node.js 20 or newer (`cd serverless/forms-worker && node --test`, no packages to install); `unittest` runs them too and skips them, saying so, when Node is missing. On Windows `python` is usually the command. `.gitattributes` keeps text files on LF line endings.

`check_site.py` fails on: a broken link, image, script or `#id`; a redirect whose target or `#id` is missing, or that chains; a root `home.html`; forbidden files in `public/` (design sources, thumbnail caches, server config backups, archives, keys, any server-script file); inline `<script>` bodies or `style=` attributes (the policy forbids them); images without `alt`.

## Bayanath
- `Bayanath.html` shows the speaker profile, the video cards, the official links, the photo slideshow and the channel card. The cards are plain HTML in the page (so search engines read them) and `portal-assets/bayanath.js` also draws them in the browser from `data/bayanath-videos.json`, so a page opened later shows the newest list. Titles are shown without the leading emoji and trailing hashtags; the full title stays in the link's tooltip; a click swaps one card for the YouTube player.
- Each card prints "Speaker: <name>" linked to the scholar profile. A video with another speaker goes in `data/bayanath-speakers.json` as `{"<11-character video id>": "Other Speaker"}` (printed, not linked) or `{"<id>": false}` (no speaker line). A video must never be attributed to the scholar if it is known to be someone else's.
- The static copy sits between `<!--bayanath:cards-->`, `<!--bayanath:recent-->` markers and in the `bayanath-jsonld` data block (keep the markers and the id). `tools/refresh_bayanath_static.py` rewrites them from the JSON; it is what the weekly workflow runs after a change. A video without an upload date is listed on the page but left out of the structured data.
- Photo slideshow: each photograph needs `alt` text; add only photographs of the speaker that the owner has the right to publish (never stock photos or search-result images, no duplicates). Photographs are shown whole.
- Aurora background: CSS gradients moved with transform and opacity only; `aurora.js` sets `--ax --ay --sx --sy`; no `touchmove` listener, no per-frame layout reads. No green on this page; keep the `prefers-reduced-motion` blocks. Never use `data-count` (`app.js` turns it into a counter).

## Security
- **Headers** (`public/_headers` for Netlify and Cloudflare Pages, `public/.htaccess` for Apache; the same values in both): a Content-Security-Policy that allows only the site's own scripts, styles, fonts, images and media (plus YouTube thumbnails and the YouTube privacy-mode player, used by Bayanath only), no inline code, no plugins, no framing; `nosniff`; a strict referrer policy; HSTS; camera, microphone, location, payment and USB off. The Residential School folder has a stricter policy of its own (`ResidentialSchoolBanikuppa/.htaccess` and its block in `_headers`); keep the copies in sync, and do not send the same header from two `_headers` rules. **GitHub Pages ignores `_headers`, `_redirects` and `.htaccess`**, so on GitHub Pages those headers and redirects do not take effect; the pages and links work as written. To get them, publish through a host that reads one of these files.
- No inline `<script>` or `style=` attributes. Never add `unsafe-inline`, `unsafe-eval` or another host to the policy without a reason. `tools/tests/test_security_headers.py` checks the headers.
- Build DOM with `textContent` and `createElement`; `innerHTML` only for fixed strings. Never put page data into an HTML string; validate ids and URLs (see `bayanath.js`). No page writes the query string or fragment into the page, or uses `eval`, `postMessage` or cookies.
- External links that open a new tab carry `rel="noopener"`. Photographs of pupils and staff are marked `noimageindex`; the one exception is the official scholar portrait, `portal-assets/speaker/mufti-maqsood-imran-rashadi.jpg`, which is left eligible for image search (`.htaccess` marks that exact path with `SetEnvIf` and skips the header for it; `_headers` never covered the speaker folder). The other photographs in `portal-assets/speaker/` keep the header on Apache. Photograph links inside `main` open in the viewer (`dialog.mo-lb`): do not add `target="_blank"` to them.
- Motion and speed: animate transform and opacity only; keep `prefers-reduced-motion` and the `html.mo-lite` exits; hidden start states (`.mo-pre`, `.mo-group`) are added by script below the fold only and removed afterwards, so a failed script never hides content. No `filter: blur()` on animated layers, no full-screen `mix-blend-mode`, no `backdrop-filter` on repeated cards (header, hero panels, dropdown, drawer and photograph viewer only; keep the `-webkit-` prefix and `@supports` fallback).
- Videos on the Jamia Masjid page use `preload="none"`, `muted`, `loop`, `playsinline` and `data-autoplay`; `masjid.js` plays them only while visible. Keep them silent. Only the first picture loads eagerly. Photographs are the owner's files, unchanged; do not crop, recompress or rename them without updating `docs/photos-provenance.json` and `docs/MASJID-MEDIA-MAP.md`.
- If Apache is the host, `Options -Indexes` is set and dotfiles, backups, logs and source maps are denied. The headers need `mod_headers`.

## Forms
Feedback, Admissions and Careers are ordinary HTML forms; `forms.js` adds the steps, validation messages and a background send. **Success is shown only when the form service answers 200 `{"ok":true}`**; otherwise the visitor's text stays in the form, a short error appears and a mail link is offered. The field names, limits, required flags and choices of each form are the rules in `serverless/forms-worker/src/schema.js`; change a field there and in the page together (`tools/tests/test_forms_worker.py` fails if they differ). While a form's `action` is the `mailto:` address and it carries `data-cx-offline`, it contacts nothing, opens the visitor's email program with the message prepared and never shows the thank-you panel. Do not add a fake or optimistic success state. Never invent an endpoint. No résumé or certificate upload is offered.

The service (`serverless/forms-worker/`) accepts POST only, reads a size cap from the stream, requires the request's Origin or Referer to be in `ALLOWED_ORIGINS`, checks a hidden field and a time trap, rate-limits by hashed visitor address, validates every field again, builds the mail subject from fixed words, sets Reply-To only after validation, echoes nothing, and answers success only when the mail provider confirmed (otherwise 503). `core.js` keeps U+200C, U+200D, U+200E and U+200F (needed for Urdu, Persian and Kannada) and removes other control characters. Secrets (`RESEND_API_KEY`, `RATE_SALT`) are Worker secrets only: never in `wrangler.toml`, the repository, a response or a log. New behaviour needs a test in `serverless/forms-worker/test/`.

## Setting up the form service (one time; needs accounts that are not part of this package)
The code is complete and tested, but it is **not live until you create the accounts and deploy it**; nothing here has been run against the real mail provider or Cloudflare. Full steps, the `curl` check and troubleshooting are in `serverless/forms-worker/README.md`. In short:
1. **Mail provider** (Resend, https://resend.com): create an account, verify the sending domain (`jameululoom.org`, by adding the DNS records it shows) and create an API key with sending access only. `MAIL_FROM` in `wrangler.toml` must be on the verified domain.
2. **Cloudflare**, in `serverless/forms-worker/`: log in, create the counter store (`npx wrangler kv namespace create FORMS_KV`) and paste its id into `wrangler.toml`, check `ALLOWED_ORIGINS`, `MAIL_TO` and `MAIL_FROM`, store the secrets (`npx wrangler secret put RESEND_API_KEY`, `npx wrangler secret put RATE_SALT` with a long random text), then `npx wrangler deploy`. It prints the Worker's address.
3. In `Feedback.html`, `Admissions.html` and `Careers.html` set the form's `action` to that address and remove `enctype="text/plain"` and `data-cx-offline`. Add the address's origin to `connect-src` and `form-action` in `_headers` and `.htaccess` (plain https, nothing else), and publish.
4. Open `Feedback.html` on the live site, send a test message and check that it arrives. `npx wrangler tail` shows the service's log (reference numbers and outcomes only).
- Limits: the rate limits use Cloudflare KV, which is not atomic (a brake on abuse, not an exact counter) and has daily write allowances on the free plan; the service keeps no copy of messages, so the mailbox is the record; a visitor without JavaScript posts the form directly and sees a small page from the service.

## Hosting on cPanel or another ordinary web host
The weekly update changes the files in this repository. A site published from the repository (GitHub Pages, or Cloudflare Pages or Netlify connected to it) is republished automatically. A site on an ordinary web host is not, so one of these has to carry the three changed files (`data/bayanath-videos.json`, `Bayanath.html`, `MuftiMaqsoodImran.html`) to the host:
1. **Automatic upload from GitHub (built in).** After a change, `.github/workflows/update-bayanath.yml` runs `tools/upload_to_host.py`, which sends the three files to the host over FTP with TLS. It is skipped unless the repository secret `CPANEL_FTP_HOST` exists. Set up once:
   - In the host's control panel create an FTP account that can reach only the site's folder, and note the FTP server name (use the name the host's certificate is issued for), the user and the password.
   - In the GitHub repository open Settings, Secrets and variables, Actions, and add `CPANEL_FTP_HOST`, `CPANEL_FTP_USER` and `CPANEL_FTP_PASSWORD`; add `CPANEL_FTP_DIR` (the site folder as the FTP account sees it, for example `/public_html`) if the account's home folder is not the site folder, and `CPANEL_FTP_PORT` only if it is not 21. If the host has no certificate that matches any usable server name, the optional secret `CPANEL_FTP_TLS_VERIFY` set to `off` skips the certificate check (the connection stays encrypted but the server's identity is not checked).
   - Upload the whole of `public/` once by hand, then start "Update Bayanath videos" from the Actions tab to test: the log shows `uploaded ...` for each file. Keep the repository in step with the live site: a page edited only on the host would be overwritten by the next upload if it is one of the three files.
2. **The host pulls from GitHub.** cPanel's "Git Version Control" can clone this repository and, with a `.cpanel.yml` file, copy `public/` into the site folder when you press "Update from Remote" and "Deploy HEAD Commit"; it does not pull by itself, so a cron job on the host (`git pull` and the deploy) is needed for a fully automatic weekly update. This needs a repository the host can read and a `.cpanel.yml` that copies only `public/` (never `.git`).
3. **Manual.** Upload the three files after each weekly run (or all of `public/`).
Moving the domain to GitHub Pages or Cloudflare Pages needs none of this.

## Weekly Bayanath updates (GitHub Actions)
`.github/workflows/update-bayanath.yml` runs `tools/update_bayanath.py` every **Saturday 21:00 India Standard Time** (cron `30 15 * * 6` in UTC; GitHub may start a scheduled run some minutes late and only runs schedules from the default branch). It reads the official channel (`@MuftiMaqsoodImran`, id `UClF-O3ig9ZKMvbeKB4t9mjQ`, from `tools/bayanath-config.json`), adds new Bayanath videos to `public/data/bayanath-videos.json`, keeps existing ones, removes duplicates and keeps the newest ten; then `tools/refresh_bayanath_static.py` rewrites the static cards and structured data in `Bayanath.html` and `MuftiMaqsoodImran.html`. Both scripts use only the Python standard library. Set `playlist_id` in the config if a verified Bayanath playlist exists; otherwise titles are filtered by `title_keywords`.
- **Manual run:** Actions tab, "Update Bayanath videos", "Run workflow". The self-tests run against a local fake YouTube and do not contact YouTube.
- **Retries:** the update step tries up to 3 times (waiting 2, then 4 minutes). If all fail, the job turns red and the committed list is untouched.
- **Safe by design:** the file is replaced only by a complete, validated list; any failure leaves the previous list; deleted or private videos are dropped; only `https` YouTube and Google addresses are contacted, redirects to other hosts are refused, response size is capped, and the API key is sent in a header only and never printed. A commit is made only when the list changed. Workflow actions stay pinned to commit hashes; keep the cron, `workflow_dispatch` and `actions: write`.
- **Publishing the change:** a push made by a workflow's own token does not start other workflows, so after committing, the job starts `deploy-pages.yml` with `gh workflow run`. **`deploy-pages.yml` must have a `workflow_dispatch:` trigger** for that to work; it is not part of this package, so check it. If the dispatch is refused the job prints a warning, the data stays committed, and the deployment is run by hand. That workflow only needs to publish `public/`; nothing has to be built first.
- **Optional secret `YOUTUBE_API_KEY`** (YouTube Data API v3, repository secret): reaches back 50 uploads and gives exact dates; without it the public RSS feed (the newest 15 uploads) is used.
- Limits: if the default branch is protected so the workflow may not push to it, the commit step fails; GitHub pauses scheduled workflows in a repository without activity for a long time (re-enable them in the Actions tab); a run that fails three times waits until the next Saturday or a manual run.
