# Jame-ul-Uloom Website

Static site (HTML, CSS and JavaScript, as the original site was), published on **GitHub Pages** by `.github/workflows/deploy-pages.yml` (that workflow belongs to the repository; this package does not replace it). **Publish `public/` as the site root.** Nothing runs on the website's own server: GitHub Pages serves files only. Everything under `tools/` is the generator (Python, build time only) and its tests. There is no database or login. Two jobs happen elsewhere, each in one place:
- the **weekly Bayanath video update** is a GitHub Actions workflow (`.github/workflows/update-bayanath.yml` with `tools/update_bayanath.py`), see "Weekly Bayanath updates";
- the **forms** (Feedback, Admissions enquiry, Careers) are sent to a small **Cloudflare Worker** (`serverless/forms-worker/`) which emails the office. It must be set up once (see "Setting up the form service"); **until then no setup message is shown on the pages**: a visitor who presses Send gets their own email program opened with the message ready, and the page says only that. A form never reports a message as sent unless the service confirms it.

## What is in `public/` (113 HTML pages, about 64 MB, of which the two large Urdu PDFs are 46 MB)
- **27 root pages.** `index.html` is the only homepage (`/home` and `/home.html` redirect to `/`). Main-portal pages: About Us, Chairmen's Messages, Governing Body, Trustees, Jamia Masjid, Services, Recognitions, Institutions, Colleges (aims, mission and vision), College Regulations, Activities, Facilities pages (Transport, Smart Classrooms, Science Laboratories, Computer Laboratory, Library, Auditorium, Sports, Calligraphy Centre, Tailoring School), Bayanath (speaker profile beside the YouTube video list), Admissions, Admissions Diary 2013-14, Contact, Careers.
- **61 institution pages** in 11 folders: `ITI/`, `PUGirlsCollege/`, `DegreeGirlsCollege/`, `BCA/`, `NCPUL/`, `EngNurSchoolDEL/`, `EngPrimarySchoolDEL/`, `EngGirlsHighSchool/`, `EngBoysHighSchool/`, `ShobaehifzDel/`, `ShobaeAlimiyathDel/`. Pages whose original text was copied unchanged from another institution are shown once, on the page they describe, and the old URL redirects there.
- **25 pages of the Residential School, Banikuppa** (`ResidentialSchoolBanikuppa/`).
- `portal-assets/images/` (photographs and scans, shown whole, never cropped), `portal-assets/documents/` (3 PDFs, unchanged originals), `data/bayanath-videos.json` (the cached video list).
- Routing and headers: `_redirects` / `_headers` (Netlify, Cloudflare Pages) and `.htaccess` (Apache) carry the same 94 legacy-URL redirects, the `/home` rule and the same security headers. They are generated; none contains credentials or server paths. **GitHub Pages ignores all three files**, so on GitHub Pages those redirects and headers do not take effect (the pages and their links work as built). To get the headers and redirects, publish through a host that reads one of these files.

## Build and check
**Requirements (build and tests only; nothing here runs on the website):** Python 3.10 or newer (3.12 is what the GitHub workflow uses) and the package `beautifulsoup4`: `python -m pip install --require-hashes -r tools/requirements.txt`. The build says so plainly if it is missing. The form service's tests need **Node.js 20 or newer** (`node --test`, no packages to install); without it they are skipped, and the test output says so. On Windows `python` is usually the command (not `python3`). `.gitattributes` keeps every text file on LF line endings so that a Windows checkout does not change generated files.
```bash
python3 tools/build.py          # school site, then root + institution pages, the form service's rules file, then the checker
(cd serverless/forms-worker && node --test)   # the form service on its own
python3 tools/check_site.py     # checker on its own
python3 -I -m unittest discover -s tools/tests -v    # unit tests (updater, workflow, forms pages, form service, security headers); the form service's Node tests are skipped if `node` is not installed
python3 tools/import_recovered_assets.py <original public_html>   # only when the recovered pictures must be re-imported
```
`check_site.py` fails on: a broken link, image, script or `#id`; a redirect whose target or `#id` is missing, or that chains; any link to or file named `home.html` at the root; forbidden files in `public/` (design sources, thumbnail caches, server config backups, archives, keys, any server-script file); inline `<script>` bodies or `style=` attributes (the CSP forbids them); images without `alt`.

## Where the content comes from
- `tools/content_main.py`, `content_more.py`, `content_inst.py`: the recovered text, written as Python so every page is regenerated. `rc_helpers.py` holds the figure, scan, table and document components.
- `tools/recovery_assets.py` lists every recovered file with its original path, alt text and caption (and `WITHHELD`, the originals that are never published); `import_recovered_assets.py` copies them byte for byte (the eight CMYK JPEGs are converted to RGB so browsers show their colours correctly).
- `tools/recognitions.json` lists the Awards & Recognition photographs (`file`, `caption`, `alt`, optional `role` and `date`); the files are in `public/portal-assets/recognitions/`.
- Historical conflicts (founding year, strengths, land area) are not resolved on the site: each figure appears only where its source states it, labelled with the source and its date.

## Not in this package, on purpose
Nothing from the server backup's private area (mail, hosting-control files, credentials, `.htaccess` backups, `cgi-bin`). Original images still withheld: the donation flyer (three copies). Its bank details are published as text on About Us, on the owner's instruction (see "Support Our Mission" below); the flyer picture itself is not. A named student's certificate is permanently excluded by decision of the website owner. Two unidentified portraits and a stock-style picture are unpublished.

## Security
- **Headers on every page** (`public/_headers`, `public/.htaccess`, generated by `tools/generate_portal.py`): a Content-Security-Policy that allows only the site's own scripts, styles, fonts, images and media (plus YouTube thumbnails and the YouTube privacy-mode player, used by Bayanath only), no inline code, no plugins, no framing (`frame-ancestors 'none'`, `X-Frame-Options: DENY`); `nosniff`; a strict referrer policy; HSTS; camera, microphone, location, payment and USB switched off. The Residential School folder adds a stricter policy of its own.
- No page writes the query string or fragment into the page, builds HTML from data, or uses `eval`, `postMessage` or cookies. Bayanath draws the video list with `textContent` only, accepts an 11-character video id and YouTube image hosts only, and ignores everything else in the JSON.
- External links carry `rel="noopener"`. Photographs of pupils and staff are marked `noimageindex`.
- The weekly Bayanath update (`.github/workflows/update-bayanath.yml`, `tools/update_bayanath.py`) pins its GitHub Actions to commits, fetches only `https` YouTube and Google addresses, refuses redirects to other hosts, never sends the API key anywhere else, and keeps the old list if anything fails. The optional `YOUTUBE_API_KEY` is a repository secret and appears nowhere in the files.
- If Apache is the host, `Options -Indexes` is set and dotfiles, backups, logs and source maps are denied. The headers need `mod_headers`. (GitHub Pages applies none of these headers; see "Build and check".)
- **Forms:** the page's CSP names the form service's address only after it is configured, and nothing else; the browser sends no cookies to it. The service accepts posts only from the website's own address, caps the request size, refuses robots (hidden field, too-fast submission), rate-limits by hashed visitor address, validates every field again, builds the email subject from fixed words, and answers success only when the mail provider confirmed. Its secrets are Worker secrets, never in the repository.

## Bayanath
- **Automatic updates:** `.github/workflows/update-bayanath.yml` runs `tools/update_bayanath.py` every **Saturday 21:00 India time** (Asia/Kolkata, UTC+05:30; GitHub evaluates cron in UTC, so the schedule is `30 15 * * 6`) and refreshes `data/bayanath-videos.json`. See "Weekly Bayanath updates" below.
- The self-tests run against a local fake YouTube; they simulate the feeds and do not contact YouTube.
- **Speaker Profile** (left column of a 40/60 two-column layout; the video cards are the right column, and on tablets and phones the speaker card comes first). Data: `tools/speaker/speaker-profile.json`; renderer: `tools/speaker/speaker.py`; photo: `tools/speaker/photo/` (the owner's file, never cropped); styles: `tools/portal-ui/bayanath.css` (loaded only on `Bayanath.html`; speaker classes start with `sp-`, video cards with `by-`, layout and background with `bz-`). Each designation carries a `verification` note for the maintainer; those notes are not shown on the page.
- **"Live Aurora Glow" background:** near-black navy with four slow CSS-gradient bands (blue, violet, teal, restrained gold; no green) that follow the pointer, a finger and the scroll position (`portal-ui/aurora.js`): eased values written to custom properties on one element, passive listeners, one frame loop that stops when nothing moves, and a self-simplifying fallback on slow devices. No images, canvas or WebGL; static under `prefers-reduced-motion`; it never blocks clicks.
- The MP3 sermons were removed at the owner's request (Bayanath is the YouTube videos plus the Speaker Profile).
- **Bayanath page layout.** Left column (narrow): the Speaker Profile (`speaker.py`, `speaker-profile.json`, the `sp-` rules in `bayanath.css`; tested against a byte-for-byte copy of the original, `tools/tests/fixtures/speaker-card-original.html`), then the **Official Social Media Links** card, which is the last thing in that column and opens the official Linktree page (`https://linktr.ee/MuftiMaqsoodImran`, new tab, `rel="noopener noreferrer"`; small portrait and generic symbols, no brand logos). Right column (wide), top to bottom: the heading **Bayanath** with its subtitle and a **View All Videos** button (the channel's video tab); the two-column video grid, drawn in the browser by `portal-ui/bayanath.js` from `data/bayanath-videos.json` (so the Saturday update still feeds it; titles are shown without the leading emoji and trailing hashtags, the full title stays in the link's tooltip; a click swaps one card for the YouTube player); the full-width **Photo Slideshow** directly under the whole grid; and the **On the official channel** card (the channel's own description, its content categories, the "Watch Lectures on YouTube" button and an expandable "Explore All Channels" panel with Linktree, Facebook, Instagram, X and WhatsApp Community). Renderer `tools/speaker/speaker_card.py` (`channel()`, `social()`, `slideshow()`), content `tools/speaker/speaker-card.json`, styles `portal-ui/bayanath.css` and `portal-ui/slideshow.css`, behaviour `portal-ui/slideshow.js`. On a phone or tablet the columns stack in the order profile, Linktree card, videos, slideshow, channel card. The slideshow shows whole photographs (never cropped) on a navy frame with a soft backdrop, a 0.7 s cross-fade, previous/next buttons, side arrows, arrow keys, swipe, one dot per photograph and a pause/play button; it advances every 10 s and holds while hovered, focused, off screen or in a hidden tab; under reduced motion it starts paused. Only the first photograph loads eagerly (the next one is requested a step ahead); a photograph that fails to load is skipped. Without JavaScript the photographs are a swipeable row and every link still works.
  **Adding a photograph:** copy the file into `tools/speaker/slides/` (JPEG, about 1600 px on the long side, under 300 KB), add one entry to `slides` in `speaker-card.json` with `file`, `alt` (what is visible), `source` (who took it or where it came from) and `rights` (the permission to use it), then run `python3 tools/build.py`. The build stops if an entry has no `source` or `rights`, or if its file is missing, and a test fails on duplicates. Only photographs you hold the right to publish, and that really show the speaker, belong here.

## Motion and speed
- **Motion layer on every page** (`portal-ui/motion.css`, `portal-ui/motion.js`, also copied into the Residential School folder): scroll reveals, gold heading line, nav underline, dropdown fade-out, staggered mobile drawer, card and photograph hover with touch equivalents, a photograph viewer (previous, next, close, keyboard, swipe), a count-up only for the real figure on Institutions, accordion polish, and a cross-fade between pages. Hidden start states are added by script only for blocks below the fold and always removed again, so a failed script never leaves content invisible. Everything is transform and opacity; `prefers-reduced-motion` turns it off.
- **Light pages:** the background orbs are plain radial gradients, the grain layer has no blend mode, repeated cards keep their tint but do not blur what is behind them, the hero slideshow and the aurora pause when off screen or when the tab is hidden, and scroll, header and back-to-top share one handler.

## Contact, Feedback, Admissions and Careers
- Four pages in one navy-and-gold design (`tools/connect/connect_pages.py` writes the text; `portal-ui/connect.css`, `portal-ui/forms.js`). Contact: copyable address, tap-to-call numbers, email, directions link, a searchable department directory. Feedback: "Your Voice Matters. Your Thoughts Inspire Us.", a four-step conversational form with star rating and topic chips, and the thank-you message. Admissions: a five-step journey, what each institution publishes, a document checklist and an enquiry form. Careers: no vacancies are invented; area cards fill in an expression-of-interest form.
- Every fact is from the existing site or the owner's printed material. Where something is not published (current fees, dates, vacancies, office hours) the page says so and points to the office. The Trust's bank details are published only on About Us, from `tools/support/support-details.json` (see "Support Our Mission").
- The forms are ordinary HTML forms; `forms.js` adds the steps, validation messages and a background send. **Success is shown only when the form service answers 200 `{"ok":true}`**; otherwise the visitor's text stays in the form, a short error appears and a mail link is offered. While sending, the button reads "Sending…". Field names, limits, required flags and choices are defined once in `tools/connect/forms-schema.json`; the pages and the service are both built from it. While `tools/connect/forms-config.json` has no `endpoint`, the forms are marked `data-cx-offline` (invisible to visitors), show no setup notice, never contact anything, and on Send open the visitor's email program with the message prepared ("Your email program should now be open…"). They never show the thank-you panel in that state.
- No résumé or certificate upload is offered (nothing sensitive is stored); the forms ask only for what the office needs.

## Deploying
1. Build (`python3 tools/build.py`), commit `public/` and the changed sources, and let `.github/workflows/deploy-pages.yml` publish `public/`. This package does not contain or change that workflow; the Bayanath workflow below only *starts* it.
2. Set up the form service once (next section). Until then the forms only open the visitor's email program (they never show the thank-you panel).
3. Nothing in the repository holds a secret. The only secrets are the optional repository secret `YOUTUBE_API_KEY` (GitHub) and the Worker secrets `RESEND_API_KEY` and `RATE_SALT` (Cloudflare).

## Setting up the form service (one time; needs accounts that are not part of this package)
The code is complete and tested, but it is **not live until you create the accounts and deploy it**; nothing here has been run against the real mail provider or Cloudflare. Full steps, the `curl` check and troubleshooting are in `serverless/forms-worker/README.md`. In short:
1. **Mail provider** (Resend, https://resend.com): create an account, verify the sending domain (`jameululoom.org`, by adding the DNS records it shows) and create an API key with sending access only. The sender in `wrangler.toml` (`MAIL_FROM`) must be on the verified domain, or the provider refuses and the forms report failure.
2. **Cloudflare**: with the current Wrangler (`npx wrangler`), in `serverless/forms-worker/`: log in, create the counter store (`npx wrangler kv namespace create FORMS_KV`) and paste the id it prints into `wrangler.toml`, check `ALLOWED_ORIGINS`, `MAIL_TO` and `MAIL_FROM` there, store the secrets (`npx wrangler secret put RESEND_API_KEY`, `npx wrangler secret put RATE_SALT` with a long random text), then `npx wrangler deploy`. It prints the Worker's address.
3. Put that address in `tools/connect/forms-config.json` (`"endpoint": "https://..."`, plain https, nothing else), run `python3 tools/build.py`, commit and deploy the site. The build refuses an address that is not plain https and adds that one origin to the CSP.
4. Open `Feedback.html` on the live site, send a test message, and check that it arrives. `npx wrangler tail` shows the service's log (reference numbers and outcomes only, no personal data).
- Limits to know: the rate limits use Cloudflare KV, which is not atomic (they are a brake on abuse, not an exact counter) and has daily write allowances on the free plan (an accepted message uses three writes); the service keeps no copy of messages, so the mailbox is the record; a visitor without JavaScript posts the form directly and sees a small page from the service.

## Weekly Bayanath updates (GitHub Actions)
`.github/workflows/update-bayanath.yml` runs `tools/update_bayanath.py` every **Saturday at 21:00 India Standard Time** (cron `30 15 * * 6` in UTC; GitHub may start a scheduled run some minutes late and only runs schedules from the default branch). It reads the official channel (`@MuftiMaqsoodImran`, id `UClF-O3ig9ZKMvbeKB4t9mjQ`, from `tools/bayanath-config.json`), adds new Bayanath videos to `public/data/bayanath-videos.json`, keeps existing ones, removes duplicates and keeps the newest ten. Visitors' browsers re-read that file every time the page opens, so once the new file is deployed a new video appears without any other change.
- **Manual run:** Actions tab, "Update Bayanath videos", "Run workflow".
- **Retries:** the update step tries up to 3 times (waiting 2, then 4 minutes). If all fail, the job turns red and the committed list is untouched.
- **Safe by design:** the file is replaced only by a complete, validated list; any failure (network, bad data, zero eligible videos, wrong channel) leaves the previous list; deleted or private videos are dropped; only `https` YouTube and Google addresses are contacted and redirects to other hosts are refused. A commit is made only when the list changed.
- **Publishing the change:** a push made by a workflow's own token does not start other workflows, so after committing, the job starts `deploy-pages.yml` with `gh workflow run` (permission `actions: write`). **`deploy-pages.yml` must have a `workflow_dispatch:` trigger** for that to work; this package does not include that file, so check it. If the dispatch is refused the job prints a warning, the data stays committed, and you run the deployment by hand.
- **Optional secret `YOUTUBE_API_KEY`** (YouTube Data API v3, repository secret): reaches back 50 uploads and gives exact dates; without it the public RSS feed (the newest 15 uploads) is used, which is enough for a weekly check.
- Limits to know: if the default branch is protected so that the workflow may not push to it, the commit step fails (allow the `github-actions` bot, or merge the data by hand); GitHub pauses scheduled workflows in a repository without activity for a long time (re-enable them in the Actions tab); a run that fails three times waits until the next Saturday or a manual run.
